# Cloud GPU pricing automation: shadow rollout

Status: shadow monitoring. Production rates and verification dates are unchanged.

## Starting point

The Monday 13:30 UTC maintenance workflow queries the Azure Retail Prices API for four mapped GPU VM SKU/region pairs. For each pair, it records the current planning rate, catalog price per GPU-hour, percentage difference, meter and product identity, currency, effective date, and a state. The Markdown report and structured `maintenance-shadow.json` are workflow artifacts. The rolling GitHub issue receives one dated observation comment per UTC day, including no-change runs, so its history survives replacement of the issue body. Re-running the workflow on the same day updates that comment.

`CHECKED_CANDIDATE` means a single candidate differs by less than 0.5% from the current rounded planning rate. `REVIEW_CHANGE` means at least 0.5%. `NO_MATCH`, `AMBIGUOUS`, and `SOURCE_ERROR` require investigation. Candidate filtering excludes Spot, Windows, reservation and non-hourly meters. A candidate is **not** a certified Linux On-Demand price or a verification of every cloud row.

## Observation period and decision gate

1. Observe at least **four scheduled weekly runs**; on the first run, independently verify the four VM configurations, GPU counts, location, Linux/standard On-Demand purchase basis, and price against the first-party Azure display. Repeat the manual check for a changed, missing, ambiguous or unexpectedly stable row. The issue history records the actual dates and outcomes; do not infer a successful run from silence.
2. Exercise fixtures that change a price, remove a SKU, duplicate a meter, introduce Spot/Windows/reservation rows, or fail a source request. These cases must surface as review signals without modifying a production rate.
3. Review the count of successful rows, exceptions, and manual findings after four runs. An unchanged price alone does not prove a correct mapping. If the source or mapping proves unreliable, keep it in shadow mode and fix the mapping.
4. Expand provider coverage using **exact purchase definitions**: AWS EC2 instance plus region and On-Demand terms; Google Cloud instance and any separately metered GPU/CPU components plus region (requires a Cloud Billing Catalog API key); Oracle Cloud GPU billing product and PAY_AS_YOU_GO USD/hour (Oracle's public product API). Identify official SKU or part numbers and independently reconcile each source before enrolling its rows. Do not substitute a GPU-only rate for a bundled node or scrape a vendor's marketing comparison as the source of truth. CoreWeave is internally preserved and commercially disabled; plan its own mapping and rights review separately.
5. Once provider coverage is reliable, create **reviewable pricing PRs** on material changes. Each proposed row needs source response evidence, exact matching purchase basis, old and new $/GPU-hour, impact on TCO scenarios, source dates, and the normal quality gate. Missing or ambiguous rows never become proposals automatically.
6. Only consider unattended merges of narrowly defined, reliably mapped list prices after successful changed-price exercises, actual production review, and row-level provenance. `CLOUD_RATES_VERIFIED_AT` is a global full-catalog date; advancing it because one provider or SKU was queried would misstate the status of the other rows. Introduce provider/row verification dates before partial automatic updates. Keep quotes, proxies, negotiated discounts, on-prem hardware, IE performance evidence, and commercial enablement under human review.

**Routine after the observation period:** the workflow checks automatically each Monday and keeps the dated history; a person reviews exceptions and refreshes the parts the sources cannot establish. GitHub issue notifications depend on the owner's subscription and GitHub notification settings. This rollout does not configure direct email, Slack, or Teams delivery, and it does not edit a pricing registry.

Source documentation: [Azure Retail Prices API](https://learn.microsoft.com/en-us/rest/api/cost-management/retail-prices/azure-retail-prices), [AWS Price List Bulk API](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/using-the-aws-price-list-bulk-api-fetching-price-list-files-manually.html), [Google Cloud Billing Catalog API](https://docs.cloud.google.com/billing/v1/how-tos/catalog-api), [Oracle list pricing API](https://docs.oracle.com/en-us/iaas/Content/Billing/Tasks/signingup_topic-Estimating_Costs.htm#AccessingListPricingforOCIProducts).
